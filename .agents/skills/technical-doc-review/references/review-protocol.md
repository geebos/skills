## 1. 角色边界

### 协调者

可创建、恢复、替换、消息、等待并停止 agent。只传事实状态：路径、分支、commit、轮次、问题 ID、已完成阶段、worker 信封。

禁止：写发现、选方案、编辑文档、核实、改状态、关闭问题、创建轮次 commit。

### Review Agent

拥有评审判断、评审记录、核实与轮次提交。每次扫描检查当前技术文档；每次核实检查实际 diff。

禁止：编辑技术文档、覆盖历史、未核对文档就关闭问题。

### Answer Agent

拥有技术结论与技术文档编辑；向评审文档追加 Answer，不覆盖历史。

禁止：关闭问题、写 Review 复核、创建 commit、切换分支、调度他人。

## 2. 评审模型

评审文档是追加-only 事件日志。

- 新问题只在发现轮定义一次；ID 从 `R001` 单调递增，禁止复用。
- 结论 ID 从 `C001` 单调递增。
- 后续 Answer / Review / 更正 / 状态迁移追加到**当前轮**，不改旧事件。
- 问题当前状态由 `### 状态变更` 中该 ID 的最新迁移派生。
- 历史错误用更正引用修正，保留原文。

终态：`已关闭`

非终态：`待处理`、`处理中`、`已回复`、`已修改`、`部分处理`、`暂不处理`、`待复核`、`需进一步确认`

仅 reviewer 可将状态迁到 `已关闭`。

## 3. 技术点标准

按独立实现决策拆分（鉴权、字段/schema、超时、重试、错误处理、事务、一致性、缓存、降级、部署、日志、数据保留等）。禁止把多决策揉成含糊总括。

每条生效结论须写明：

1. 采用方案  
2. 不采用方案（或明确无备选）  
3. 适用范围  
4. 不适用范围  
5. 前置条件  
6. 关键约束  
7. 错误/失败/降级  
8. 验证或验收方法  

影响行为/边界/验收时，标记模糊用语（可以、建议、推荐、尽量、原则上、视情况而定、按需处理、根据实际情况决定、必要时、合理设置、适当调整、后续确定）。仅当其后有客观条件且每条件唯一结果时才可保留。

交叉核对正文、示例、表格、图、时序图、API、附录、配置、伪代码；任一冲突即问题。

### 未决点

完成前关键决策不得悬空。未决须记录：问题与状态、不能决定的原因、候选与差异、责任人、截止时间、所需输入、临时结论；豁免须有例外原因与后续流程。缺任一项无效。`部分处理` / `暂不处理` / `需进一步确认` 一律进入下一轮。

## 4. 问题与状态规则

**新问题**字段：技术点、提出 Commit、当前描述、问题、风险、Review 建议、必须明确的结论、状态（初始 `待处理`）。

**Answer**字段：最终结论、不采用方案、适用范围、不适用范围、前置条件、关键约束、异常处理、验证方式、修改位置、修改内容、状态（通常 `待复核`）。

**Review**字段：结论是否唯一/明确/可执行/可验证、适用范围与前置条件是否明确、约束与异常是否完整、Answer 与文档是否一致、是否存在或引入冲突、复核结论、后续要求、最终状态、关闭 Commit（关闭时用 `当前记录所在 Commit`）。

不得关闭：文档未改、仍有备选、措辞裁量、范围缺失、依赖实现时判断、表述冲突、验证未说明。新问题用新 ID。

## 5. 追加-only 轮次结构

结构以 [assets/review-document-template.md](../assets/review-document-template.md) 为准。摘要：

```markdown
# Review：`<document-name>.md`

## 基本信息
* 技术文档 / Review 文档 / Review 分支 / 基准分支
* Review Agent / Answer Agent

## Round N
* 起始 Commit / 技术文档 Commit / 完成 Commit：当前记录所在 Commit

### 新增问题
#### R00x：标题
* …
##### Answer
* …
##### Review
* …

### 本轮技术结论
### 状态变更
### 未关闭问题

## Review 完成   # 仅终轮
```

- 每轮保留四个子节；无内容写 `* 无`。
- Answer / Review 必须挂在对应 `#### R00x` 下，用 `##### Answer` / `##### Review`。
- 后续轮次不重复填写完整问题定义；可在本轮 `### 新增问题` 下再次使用 `#### R00x：…` 作为锚点，仅追加 Answer / Review。
- 更正示例：`> 更正记录（Round N）：…原记录保留。`

## 6. Git 语义

- **分支预检**由 skill 调用方在启动协调者之前完成：干净工作区 → 基线（默认 `main`）pull → 创建/切换 `review/<document-name>` → 记录起始 commit → 必要时复制评审模板。协调者与 worker 不再做预检。
- 两 worker 同 worktree、同 review 分支、串行。
- 轮次 commit：仅 reviewer 在扫描→回答→编辑→核实→记录→状态更新完成后执行；只 `git add` 技术文档与评审文档。
- 消息：`docs(<document-name>): complete review round <N>`
- 不要在 review 分支上 squash 多轮。
- 自引用字段写 `当前记录所在 Commit`；提交后可用 `git log -1 --format=%H -- <file>` 解析。

## 7. 恢复与交接

协调者在每次有效 worker 结果后更新快照（路径、branch、round、head、completed_phase、open_issue_ids、线程 id）。失败先恢复原线程；不可用则同类型替换并传入快照。异常不算完成阶段。

## 8. 完成门禁

仅 reviewer 可宣布完成，且须同时满足：

- 每个独立技术点有一条生效结论  
- 范围、前置、约束、失败、验证均明确  
- 各表述一致  
- 全部问题最新状态为 `已关闭`  
- 新扫描无新问题  
- 每轮有一次完整轮次 commit  
- 已追加 `## Review 完成`  
- 最终 commit 后工作区干净  
- `validate_review.py --mode complete` 通过  

完成不授权合并；遵循仓库策略与用户授权。
