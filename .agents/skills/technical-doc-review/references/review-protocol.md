# 技术文档评审协议

本文件约定**评审文档与技术文档**的公共结构、状态语义与质量标准。执行方只按自己的任务提示操作文档；不涉及调度、恢复或其它执行方。

## 目录

结构样例以 [assets/review-document-template.md](../assets/review-document-template.md) 为准。

## 1. 公共工作约定

1. 动手前完整阅读：当前技术文档、当前评审文档、本协议与模板。
2. **只追加，不改写历史**：禁止删除、覆盖或改写既有段落；纠错用更正引用，保留原文。
3. 只处理调用方指派的路径与轮次；不切换基线分支、不创建分支、不 `git pull` 基线。
4. 当前应在 `review/*` 分支上工作；若分支或工作区明显异常，停止并在结果信封中报告，不自行改分支。
5. 技术文档与评审文档中的结论必须可执行、可验证；禁止空泛确认语（如「已确认」「后续处理」「实现时决定」）。
6. 交叉核对正文、示例、表格、图、时序图、API、附录、配置与伪代码；任一表述冲突都必须作为问题处理或在结论中消解。
7. 影响行为、边界或验收的模糊用语须消除或补全客观条件：可以、建议、推荐、尽量、原则上、视情况而定、按需处理、根据实际情况决定、必要时、合理设置、适当调整、后续确定。
8. 每步结束输出调用方要求的 YAML 结果信封；缺字段、格式错误或与仓库事实矛盾视为本步未完成。

## 2. 评审模型

评审文档是追加-only 事件日志。

- 新问题只在**首次提出**时写完整定义；问题 ID 从 `R001` 单调递增。
- 结论 ID 从 `C001` 单调递增。
- 后续处理追加在**当前轮**对应问题下，不改旧事件。
- 问题当前状态由 `### 状态变更` 中该 ID 的**最新**迁移派生；无状态事件时以问题定义中的状态为准。
- 历史笔误用更正引用，例如：`> 更正记录（Round N）：…原记录保留。`

**终态**

- `已关闭`

**非终态**

- `待处理`、`处理中`、`已回复`、`已修改`、`部分处理`、`暂不处理`、`待复核`、`需进一步确认`

`已关闭` 仅允许写在 `##### Review` 的最终状态，以及据此汇总的 `### 状态变更`。其它区块不得将问题标为 `已关闭`。

## 3. 技术点标准

按**独立实现决策**拆分文档。典型独立点：鉴权、字段/schema、超时、重试、错误处理、事务边界、一致性、缓存、降级、部署拓扑、日志、数据保留等。禁止把多个决策揉成含糊总括。

每条生效结论须同时写明：

1. 采用方案  
2. 不采用方案（或明确无备选）  
3. 适用范围  
4. 不适用范围  
5. 前置条件  
6. 关键约束  
7. 错误 / 失败 / 降级行为  
8. 验证或验收方法  

### 未决点

完成前，关键决策不得悬空。若暂时不能定案，须记录：问题与状态、不能决定的原因、候选与差异、责任人、截止时间、所需输入、临时结论；若申请豁免，写明例外原因与后续流程。缺任一项视为无效。`部分处理`、`暂不处理`、`需进一步确认` 均不得当作完成。

## 4. 问题与状态规则

### 问题定义（`#### R00x：标题`）

必填：技术点、提出 Commit、当前描述、问题、风险、Review 建议、必须明确的结论、状态（新问题初始为 `待处理`）。

### `##### Answer`

必填：最终结论、不采用方案、适用范围、不适用范围、前置条件、关键约束、异常处理、验证方式、修改位置、修改内容、状态（成功处理时为 `待复核`；受阻时为非终态并写明阻塞信息）。

本区块**不得**：

- 写入 `##### Review`
- 将状态设为 `已关闭`
- 执行 `git commit` / 切换分支

### `##### Review`

必填：结论是否唯一/明确/可执行/可验证、适用范围与前置条件是否明确、约束与异常是否完整、`##### Answer` 与技术文档是否一致、是否存在或引入冲突、复核结论、后续要求、最终状态；关闭时关闭 Commit 写 `当前记录所在 Commit`。

**不得关闭**（最终状态不得为 `已关闭`）当：技术文档未改、仍有未排除备选、措辞仍裁量、范围缺失、依赖实现时判断、表述冲突、验证未说明、`##### Answer` 与 diff 不一致。

新发现问题使用**新**问题 ID，不得并入旧问题定义。

### 汇总小节

- `### 本轮技术结论`：本轮生效的 `C00x` 及关联问题 ID  
- `### 状态变更`：`* R00x：旧状态 → … → 新状态`  
- `### 未关闭问题`：仍非 `已关闭` 的 ID 列表；全无则 `* 无`

## 5. 追加-only 轮次结构

```markdown
# Review：`<document-name>.md`

## 基本信息
* 技术文档 / Review 文档 / Review 分支 / 基准分支
* Review Agent / Answer Agent   # 固定标识字符串，与校验器一致

## Round N
* 起始 Commit / 技术文档 Commit / 完成 Commit：当前记录所在 Commit

### 新增问题
#### R00x：标题
* …
##### Answer
* …
##### Review
* …

### 本轮技术结论
### 状态变更
### 未关闭问题

## Review 完成   # 仅全部完成时追加
```

- 每一 `## Round N` 必须含四个 `###` 子节；无内容写 `* 无`。
- `##### Answer` / `##### Review` 必须挂在对应 `#### R00x` 下。
- 后续轮次可为既有 ID 再建 `#### R00x：…` 锚点并只追加新的 Answer/Review，不重复改写首次定义字段。
- 自引用 commit 字段一律写 `当前记录所在 Commit`（文件不能包含「含本文件的那次 commit」的 hash）。

## 6. Git 与提交语义

- 工作分支已是 `review/<document-name>`；不要改回基线、不要新建分支。
- **轮次提交**仅在：本轮问题已处理、`##### Review` 已写完、状态已汇总、结构校验通过之后执行。
- 只暂存技术文档与对应评审文档：

```bash
python3 .agents/skills/technical-doc-review/scripts/validate_review.py \
  <document-name>.md review-<document-name>.md --mode round

git add <document-name>.md review-<document-name>.md
git commit -m "docs(<document-name>): complete review round <N>"
```

- 禁止 `git add .`；禁止把多轮 squash 成一次提交。
- 完成提交后可用 `git log -1 --format=%H -- <file>` 解析真实 hash。

## 7. 完成门禁

仅当下列全部成立时，才可追加 `## Review 完成` 并做完成校验：

- 每个独立技术点有一条生效结论  
- 范围、前置、约束、失败路径、验证均明确  
- 各表述一致  
- 全部问题最新状态为 `已关闭`  
- 再扫一遍无新问题  
- 每轮已有对应轮次 commit  
- 已追加 `## Review 完成`（字段见模板）  
- 最终 commit 后工作区干净  
- `validate_review.py --mode complete` 通过  

完成块中的数值字段须与文档事实一致。完成**不等于**授权合并。
